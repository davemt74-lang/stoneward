# Canvas ideas and project approval

The user menu places **Canvas ideas** and **Auto-approve agent projects** beside the Coding Model selector. Both preferences are saved per account. Ideas default on; auto-approval defaults off. **Suggest a canvas** requests one fresh concept using the account’s own recent canvas history and published artist context. There is no paid planning on page load or a timer.

By default, a new canvas or revision presents a short concept in chat before code or image generation. **Approve project** starts that exact project; **Revise** prepares a replacement for review, and **Cancel** ends the proposal. `/approve` and `/cancel-project` act on the current review. Turning off ideas stops idea suggestions and makes user-directed planning use the submitted brief without a model call; it does not turn off project approval. Turning on auto-approval allows the account’s future proposals to proceed directly. Turning it off revokes unconsumed automatic approvals.

Planning uses the selected enabled coding model and the existing Active Tokens reservation and settlement system. Idempotent planning request IDs reuse an in-progress or completed result without another charge. Code and image generation retain their own existing accounting after approval. Existing deliberate image-edit and saved-image replacement confirmations remain independent.

New canvases save the actual submitted `design_brief`. Earlier canvases without one supply their real saved code and metadata as reference material; the agent never invents an original prompt. An idea may reinterpret, integrate or combine owned source canvases, or propose a new experience. The model selects from the supplied history; there are no required visual templates or generated widgets. The planning context has a byte budget and uses up to twelve recent owned canvases. Build context reloads and validates all selected owned sources, with explicit truncation metadata when code exceeds its context budget.

`api/canvas-projects.php` requires authentication and CSRF for writes. GET returns private preferences and pending proposals. POST supports `preferences`, `propose`, `suggest`, `approve` and `cancel`. Responses expose the reviewed build snapshot as `proposal.project`. Account changes abort client requests and remove private proposal cards. Privacy exports include proposals and settings; history clearing invalidates pending work and account closure removes it.

The public UI sends code builds with `project_managed: true` and `proposal_id`. The server verifies ownership, current approval and the exact brief, model, music/image inputs, source canvases and song context before paid execution. The first build request binds its request ID, allowing safe replay but preventing a second build from the same approval. A changed scope requires a new proposal. Legacy direct API callers remain compatible; their explicit execution requests retain their existing behavior.

Validation: `tests/canvas-projects.php`, `tests/canvas-project-ideas.php`, `tests/canvas-project-privacy.php`, `tests/canvas-projects-http.py` and `tests/canvas-projects-browser.py` cover approval, snapshots, settings, owner separation, token idempotency, privacy resets and the mobile/desktop chat controls.
