# Music data and playback in custom canvases

Type `/music` in a canvas prompt to choose public songs or albums. Choosing an album selects its available MP3 tracks in release order; shared songs are deduplicated and each song remains an independent input. The picker inserts `{music-track:ID}` bindings. `/music-all` inserts `{music-all}` for the current full public MP3 catalog. Both can be combined with image inputs and `/edit`.

Music inputs are saved with the private canvas as `music_inputs: {mode: 'selected', track_ids: [...]}` or `{mode: 'all'}`. Edits retain the selection until a new one is supplied. The selection scopes `StonefellowAudio.catalog()`, source access and playback requests. Selected songs retain their order; all mode resolves the current published MP3 catalog without a fixed track-count limit. Reopening rechecks source availability. The coding model creates the requested presentation and interactions from these audio nodes.

`api/site-data.php` provides the public music catalog and published releases. The Coding Agent also receives registered canvas data tools and a ranked public release index with real release IDs, titles and track counts. It chooses the data and designs the presentation from the user's prompt.

`published_release_tracks` supplies public songs in the release's stored track order. It includes `release_id`, `release_title`, `track_id`, `title`, `duration_seconds` and `position`. Exact `release_id` and `track_id` filters apply before the 120-row delivery limit, so a requested release is not lost behind earlier catalog entries. Hidden releases, unpublished songs, missing songs and duplicate membership are excluded.

The model declares a dataset container and one `sf-data-row` template. Empty `sf-field-title` and other field elements receive live values. For playable rows, a descendant with `sf-action-play-track` becomes a real button bound to that row's canonical song ID. Both `published_catalog` and `published_release_tracks` advertise this action. The model controls layout, colors and styling; the host supplies data and playback behavior.

Custom canvases can include their own `js` source alongside HTML and CSS. Code runs in the isolated canvas document with a server-derived source hash. `window.StonefellowAudio` supplies async `catalog(filters?)`, `getTrack(id)`, `getAudio(id)`, `releaseAudio(id)`, `play(id?)`, `pause()`, `seek(seconds)`, `setVolume(0..1)` and `getState()`. `catalog` returns `{tracks,releases}` and accepts `release_id` or `track_id`. `getAudio` returns `{track,blob,url}` for the current published MP3; code can use those bytes for local playback or processing. `subscribe(listener)` returns an unsubscribe function and publishes the main player's track ID, title, time, duration, playing, ended, volume and mute state.

The coding agent creates the interface requested by the user. Canonical playback methods operate the existing main player and footer player; raw MP3 processing remains available for other requested audio experiences. The previous injected `sf-host-playback` control strip is removed, including when reopening older saved canvases. A track list alone does not add a transport section.

The public `api/canvas-audio.php?action=catalog` endpoint returns safe published track/release metadata. `action=source&track_id=ID` rechecks publication and the current public MP3 source before serving GET/HEAD and byte ranges. Protected originals, hidden releases and arbitrary source URLs are excluded. The host loads the bytes for the sandbox. Canvas code has no ambient network access, and the parent frame policy blocks self-navigation requests. Source text is JSON-escaped and executed through a fixed hashed runner so literal script-tag strings cannot break the document.

The Coding Agent panel starts closed when a saved canvas is restored. Its footer **Code** button opens and closes the source rail without stopping the canvas program or an active build. Source includes HTML, CSS and optional JavaScript. Closing the canvas releases its audio requests, subscriptions and object URLs.

Existing saved HTML containing copied song titles remains the saved design. Revising that canvas lets the agent replace its static list with a live dataset and playback bindings. The application does not guess song identities from visible text or replace the user's layout with a predefined playlist widget.

Canonical canvas playback resolves each track through the freshly authorized MP3 source endpoint, including when the page catalog still has an older listening URL. The track metadata and listening history continue to use the same stable track ID. Local custom audio processing uses the Blob URL returned by `StonefellowAudio.getAudio(track.track_id)`; catalog URLs are host references and cannot be loaded directly by a sandboxed canvas.

Runtime audio diagnostics join the existing `ddd` copyable report. They record SDK readiness/play requests and sanitized failure codes for canonical controls, local media, browser permission and media CSP blocks. Records are scoped to the current account/canvas, bounded to 40 per SDK host, and contain no raw media URLs, provider messages or authored code. The diagnostic observer preserves local playback sources, timing and the native play promise; it does not retry or rewrite canvas code. Reproduce a failure, open `ddd`, and use Copy to capture the report from that tab.

Completed-track replay resets the saved resume checkpoint to zero before a source refresh. A genuinely incomplete file keeps its verified progress. Runtime diagnostics now include the failing stage (catalog, selection, site catalog, playback, resume seek or session), with a distinct audio_seek_unavailable code for an impossible saved seek.

The canvas SDK exposes `id` as a canonical alias of each track's `track_id` and each release's `release_id`. Track-reference methods (`play`, `getTrack`, `getAudio`, `releaseAudio`) accept a string ID or a song object with consistent `track_id`/`id` fields. `play()` with no argument resumes the current song; explicitly missing/null or conflicting references fail validation rather than choosing another song. This compatibility applies when reopening older canvas code without rewriting its interface or selecting a default song.

For independent playback, `await StonefellowAudio.createPlayer(trackRef)` returns a code-only handle with async `play()`, `pause()`, `seek(seconds)`, `setVolume(0..1)`, `getState()` and `dispose()`. Its synchronous `subscribe(listener)` immediately supplies its own frozen state and returns an unsubscribe function. State has the same `trackId`, `title`, `currentTime`, `duration`, `playing`, `volume`, `muted` and `ended` fields as synchronized playback. The handle controls a native Audio element owned by the host; it adds no buttons, album panel, or other presentation. The coding agent builds the interaction and UI requested by the user.

Creating a handle verifies the selected public track and loads an authorized MP3 Blob without starting playback. Each `play()` rechecks the current public catalog and canvas selection. Its private Blob URL stays in the host. Native playback failures reject with safe codes, including `audio_gesture_required`; code should invite a user gesture rather than invent playback, request microphone access, or retry automatically. There can be up to 32 live independent handles in one canvas session; dispose inactive handles to release capacity. Downloads, metadata preloads, sandbox-authored events, and `getAudio()` processing or local playback are not verified listening events. Use synchronized `play()` for the main/footer player, or `createPlayer()` for independently observed playback.

The host captures the canvas or approved-gallery identity when mounting the audio session and attaches it to the native observer. Author code cannot supply a different attribution context. Pausing, buffering, seeking and source failures follow the shared listening process; skipped positions do not add listening time. Independent handles retain their own play identity across pauses and resumes, while synchronized SDK/main/footer controls observe the same single canonical player. Explicit disposal, canvas replacement, close, and account/access revocation stop independent media, cancel pending work, release subscriptions, and revoke host Blob URLs. Hiding the agent or Code panel preserves the session and playback.
